## Context

当前后端已经有 `CalorieEntry` 记录模型和 `VercelAiClient` 通用 AI 客户端，但单条记录相关接口仍停留在 CRUD，无法为某一条饮食或运动记录生成即时点评。用户这次需求要求前端只传记录 ID，后端自行查记录、区分饮食/运动、调用固定模型并返回简短点评。

现有模块关系里，`VercelGatewayModule` 已依赖 `CalorieModule`，如果直接让 `CalorieModule` 反向导入 `VercelGatewayModule` 来复用 AI client，会形成循环依赖。因此这次变更不仅是新增接口，还涉及一处共享 AI 能力的依赖整理。

## Goals / Non-Goals

**Goals:**
- 为已认证用户提供按记录 ID 生成单条 AI 点评的接口
- 保证请求无需传提示词、记录内容或模型名，由后端基于记录数据自行构造上下文
- 对饮食和运动记录分别生成更贴合场景的点评内容
- 固定使用 `gpt-5.4-nano`，并对返回文本做轻量规范化，确保输出简练、直接、40 字以内
- 在不新增数据库结构的前提下复用现有 `CalorieEntry` 字段和 AI 客户端能力

**Non-Goals:**
- 不持久化 AI 点评结果，不新增 comment 字段或新集合
- 不支持批量点评多条记录
- 不开放自定义提示词、模型切换或语气配置
- 不改变现有 `/gateway/ai/suggest` 的行为

## Decisions

### 决策 1：接口归属到 `CalorieController`

**选择**：新增 `POST /calorie/:id/comment`，请求只包含路径参数中的记录 ID。

**原因**：点评对象本质上是单条卡路里记录的派生能力，放在 `calorie` 资源下更符合现有 CRUD 路由风格，也能直接复用“按当前用户查询该记录”的权限边界。

**备选方案**：放到 `VercelGatewayController`，例如 `POST /gateway/ai/calorie-entry-comment`。该方案虽然能复用现有网关模块依赖，但会把资源读取逻辑和 AI 入口耦合在网关模块里，削弱 `calorie` 领域的一致性，因此不采用。

### 决策 2：抽出共享 AI 模块，避免 `CalorieModule` 与 `VercelGatewayModule` 循环依赖

**选择**：将 `VercelAiClient` 提升为独立可复用的共享模块（例如 `AiModule`），由 `CalorieModule` 和 `VercelGatewayModule` 分别导入。

**原因**：当前 `VercelGatewayModule` 已导入 `CalorieModule`，若沿用“从网关模块导出 client”的方式，会导致反向导入。抽出共享模块可以保持依赖单向流动，也与项目现有的 NestJS 模块化风格一致。

**备选方案**：
- 在模块之间使用 `forwardRef` 强行消除循环。拒绝，因为这会扩大耦合并让后续 AI 能力扩展变得更脆弱。
- 在 `CalorieService` 内直接复制 HTTP 调用逻辑。拒绝，因为会重复现有 AI 网关封装。

### 决策 3：由后端基于记录字段构造类型化 prompt

**选择**：后端读取记录后，按 `type` 区分饮食/运动，使用固定 system prompt 约束输出风格，并将 `title`、`calories`、`description`、`mealType`、`duration`、`entryDate` 等字段整理成 user message。

**原因**：用户明确要求“请求只传记录 id”，因此 prompt 和上下文都必须由后端生成。类型化组织上下文能让饮食记录更关注食物健康度，运动记录更关注强度与积极反馈。

**备选方案**：
- 直接把整条记录 JSON 原样喂给模型。可实现但可读性较差，也不利于稳定控制语气和长度。
- 允许前端传补充文案。拒绝，因为与“只传记录 id”要求冲突。

### 决策 4：固定模型并在服务端做输出规范化

**选择**：调用 `VercelAiClient.chatWithModel('openai/gpt-5.4-nano', ...)`，对返回文本执行 `trim`、去换行、长度上限控制等轻量规范化，最终返回 `{ comment, model }`。

**原因**：这次点评场景是短文本、单轮、低延迟诉求，固定模型有助于结果稳定；仅靠提示词无法保证始终满足 40 字以内，因此服务端需要做最小限度的兜底处理。

**备选方案**：完全依赖提示词，不做后处理。拒绝，因为无法稳定满足输出约束。

### 决策 5：AI 或记录查询失败时返回明确错误，不降级为伪点评

**选择**：记录不存在或不属于当前用户时返回 404；AI 网关调用失败或返回不可解析文本时返回 502。

**原因**：点评结果是派生能力，不应在失败时返回看似成功但不可信的默认文案，否则前端无法区分真实点评与系统兜底。

## Risks / Trade-offs

- [共享 AI 模块重组会触及现有网关模块导入关系] → 通过保持 `VercelAiClient` API 不变、仅调整 provider 归属来降低回归风险，并补充现有 AI 建议回归测试。
- [模型偶发输出超过 40 字或带寒暄] → 服务端增加轻量规范化，但仍保留提示词为主要约束，避免过度裁剪导致语义失真。
- [单条记录字段不完整时点评上下文不足] → 采用“核心字段必带、缺失字段省略”的 prompt 组装方式，不因描述缺失而阻塞点评。
- [固定模型名称与网关可用模型存在环境差异] → 在实现时将模型名集中为常量，便于后续调整，同时在测试中验证传入模型值正确。

## Migration Plan

1. 抽出共享 AI 模块并回归现有 `/gateway/ai/suggest` 路由。
2. 为 `calorie` 模块新增点评路由、服务方法和响应 DTO。
3. 添加单元测试覆盖记录归属校验、prompt 构造、模型选择和输出规范化。
4. 部署后由前端切换到新接口，无需数据迁移；若出现异常，可仅回滚新增路由和共享模块拆分。
